# 커리큘럼 버전 관리 로드맵 설계

## 배경

코스 콘텐츠는 운영 중에도 바뀔 수밖에 없다. 오탈자 수정, 예제 추가, 레슨 삽입, 챕터 재배치, 오래된 레슨 제거는 모두 실제 교육 서비스에서 자연스럽게 발생한다. 따라서 한 번 공개한 코스를 절대 수정하지 않는 방식은 현실적인 해법이 아니다.

문제는 변경 자체를 막는 것이 아니라, 변경이 학습자의 진행 상태와 성취를 흔들지 않도록 전달하는 것이다. 특히 완료 레슨, 완료율, 스트릭, 배지 같은 성취 기반 정보가 구조 변경으로 사라지면 학습자는 플랫폼을 신뢰하기 어렵다.

이 설계는 관리자 콘텐츠 관리 기능을 곧바로 만들기 전에, 콘텐츠 변경을 안전하게 다룰 수 있는 로드맵과 단계별 구현 경계를 고정한다.

## 핵심 원칙

- 학습자가 이미 완료한 성취는 콘텐츠 구조 변경 때문에 사라지지 않는다.
- 콘텐츠는 불변 객체가 아니라 버전이 있는 커리큘럼으로 다룬다.
- 마이너 편집과 구조 변경은 같은 정책으로 처리하지 않는다.
- 삭제는 기본적으로 금지하고, 신규 노출 중단은 아카이빙으로 처리한다.
- 기존 학습자와 신규 학습자는 서로 다른 커리큘럼 버전을 볼 수 있다.
- 구조 변경은 새 버전 발행과 명시적인 마이그레이션 정책을 통해서만 기존 학습자에게 적용한다.
- 관리자가 직접 수정하는 draft와 학습자가 보는 published 버전을 분리한다.
- 로드맵의 각 단계는 독립적으로 테스트, 문서화, 배포할 수 있어야 한다.

## 현재 구조

현재 콘텐츠 스키마는 코스, 챕터, 레슨이 직접 연결되어 있다.

```text
courses
  -> course_chapters
    -> course_lessons
      -> lessons
        -> lesson_steps
```

학습 진행은 콘텐츠 ID에 직접 귀속된다.

```text
course_progress
  - user_id
  - course_id
  - last_lesson_id
  - completed_count

lesson_progress
  - user_id
  - lesson_id
  - course_id
  - current_step_id
  - status
```

이 구조에서는 관리자가 기존 챕터나 레슨을 삭제하거나 순서를 바꾸면, 진행률 계산과 다음 레슨 계산이 최신 콘텐츠 구조에 바로 영향을 받는다. 따라서 관리자 CMS를 먼저 만들면 학습자 상태 보존 규칙을 나중에 덧붙이기 어렵다.

## 접근 대안

### 대안 A: 관리자 CMS 우선

코스, 챕터, 레슨 생성·수정·삭제 API와 화면을 먼저 만든 뒤 버전 관리를 추가한다.

장점은 운영 화면을 빠르게 만들 수 있다는 점이다. 단점은 콘텐츠 변경이 학습 진행 데이터에 직접 영향을 주는 현재 구조를 더 오래 유지하게 된다는 점이다. 이후 버전 관리 도입 시 이미 만들어진 수정 API와 UI를 다시 고쳐야 한다.

### 대안 B: 버전 경계 우선

커리큘럼 버전 모델과 학습 진행 버전 귀속을 먼저 도입하고, 그 다음 관리자 편집과 발행 워크플로우를 만든다.

장점은 학습자 성취 보존 원칙을 데이터 모델에서 먼저 보장할 수 있다는 점이다. 단점은 운영자가 당장 사용할 수 있는 편집 UI가 늦어진다는 점이다.

### 대안 C: 전체 버저닝 일괄 구현

버전 모델, draft/published 발행, 마이그레이션 맵, 학습자 업그레이드 UX, 공지까지 한 번에 구현한다.

장점은 최종 제품에 가까운 그림을 한 번에 완성할 수 있다는 점이다. 단점은 변경 범위가 너무 넓어 테스트와 리뷰가 어려워지고, 현재 읽기 중심 어드민 구조에서 불필요하게 큰 위험을 만든다는 점이다.

## 권장안

대안 B를 채택한다. 먼저 전체 로드맵을 고정하고, 구현은 버전 경계부터 순차적으로 진행한다.

관리자 CMS보다 버전 경계를 먼저 세우는 이유는 학습자 진행 데이터가 플랫폼의 신뢰 기반이기 때문이다. 콘텐츠 운영 편의는 중요하지만, 완료 성취가 사라지지 않는다는 약속이 먼저 데이터 모델에 반영되어야 한다.

## 목표 도메인 구조

커리큘럼은 코스의 특정 버전으로 표현한다.

```text
Course
  -> CurriculumVersion
    -> VersionChapter
      -> VersionLesson
        -> Lesson
          -> LessonStep
```

학습 진행은 코스 자체가 아니라 학습자가 시작한 커리큘럼 버전에 귀속한다.

```text
LearnerProgress
  - userId
  - courseId
  - curriculumVersionId
  - lastLessonId
  - completedLessonIds
```

기존 코스와 레슨 ID는 가능한 한 유지한다. 버전 모델은 학습자가 어떤 구조를 기준으로 진행 중인지 명확히 하기 위한 경계이며, 모든 본문 콘텐츠를 처음부터 완전한 immutable snapshot으로 복제하는 것은 1차 목표가 아니다.

## 변경 유형

콘텐츠 변경은 다음 유형으로 분류한다.

| 변경 유형        | 예시                                     | 정책                                                                  |
| ---------------- | ---------------------------------------- | --------------------------------------------------------------------- |
| `minor-edit`     | 오탈자 수정, 설명 보완, 이미지 교체      | 같은 버전에 즉시 반영할 수 있다. 학습자 공지는 필요하지 않다.         |
| `additive`       | 기존 레슨 안의 예제 추가, 보충 설명 추가 | 같은 버전에 반영할 수 있다. 필요하면 선택 공지를 제공한다.            |
| `structural`     | 새 레슨 삽입, 챕터 순서 변경, 레슨 이동  | 새 버전을 발행한다. 기존 학습자는 현재 버전을 유지한다.               |
| `major-revision` | 커리큘럼 전면 개편, 다수 레슨 병합·분할  | 새 버전 발행과 마이그레이션 맵을 요구한다. 학습자 선택 UX가 필요하다. |

관리자 CMS가 추가될 때는 관리자가 변경 유형을 명시하거나, 구조 변경 여부를 시스템이 감지해 발행 정책을 제한한다.

## 삭제 정책

레슨과 챕터는 실제 삭제하지 않는다. 신규 학습자에게 더 이상 보여주지 않으려면 상태를 변경한다.

```ts
type CurriculumNodeStatus = "active" | "deprecated" | "archived"
```

- `active`: 신규 학습자와 기존 학습자 모두에게 정상 노출한다.
- `deprecated`: 대체 예정 상태다. 기존 학습자는 접근할 수 있고, 관리자 화면에서는 정리 대상임을 표시한다.
- `archived`: 신규 학습자 경로에서는 숨긴다. 기존 학습자의 완료 기록과 이전 버전 조회를 위해 데이터는 보존한다.

실제 삭제는 운영 복구 기간, 감사 로그, 진행 데이터 참조 여부를 확인한 뒤 별도 정리 작업에서만 다룬다. 1차 로드맵에서는 실제 삭제 기능을 만들지 않는다.

## 단계형 로드맵

### 1단계: 정책 문서화

목표는 콘텐츠 변경 정책을 도메인 문서에 먼저 고정하는 것이다.

포함 범위:

- 변경 유형 정의
- 삭제 대신 아카이빙 원칙
- 완료 성취 보존 원칙
- 구조 변경 시 버전 업 원칙
- 관리자 CMS가 따라야 할 발행 규칙

완료 조건:

- `DOMAIN.md`, `BACKEND.md`, `/docs` 문서에 정책이 반영된다.
- 이후 구현 단계가 이 정책을 기준으로 테스트 조건을 세울 수 있다.

### 2단계: 커리큘럼 버전 모델 추가

목표는 현재 콘텐츠를 각 코스의 `v1` published 버전으로 귀속시키는 것이다.

추가 후보 테이블:

```text
curriculum_versions
  - id
  - course_id
  - version_number
  - status
  - title
  - changelog
  - published_at
  - created_at

curriculum_version_chapters
  - id
  - curriculum_version_id
  - source_chapter_id
  - label
  - title
  - sort_order
  - status

curriculum_version_lessons
  - id
  - curriculum_version_id
  - chapter_id
  - lesson_id
  - title
  - description
  - sort_order
  - status
```

`status`는 `draft`, `published`, `archived` 같은 버전 발행 상태와 챕터·레슨 노드 상태를 구분해서 설계한다. 실제 구현 시 이름 충돌을 피하기 위해 버전 상태와 노드 상태 타입을 분리한다.

완료 조건:

- 기존 seed 콘텐츠가 각 코스의 `v1` published 버전으로 조회된다.
- 공개 코스 목록과 코스 상세는 최신 published 버전 기준으로 기존 응답을 유지한다.
- 기존 API 응답 형태를 불필요하게 깨지 않는다.

### 3단계: 학습 진행의 버전 귀속

목표는 학습자가 어떤 커리큘럼 버전을 기준으로 진행 중인지 저장하는 것이다.

변경 후보:

```text
course_progress
  - curriculum_version_id

lesson_progress
  - curriculum_version_id
```

`lesson_progress`에도 버전 ID를 둘지 여부는 구현 전 테스트 설계에서 확정한다. 코스 진행의 버전만으로 충분하면 중복을 줄이고, 레슨 단위 검증이 필요하면 명시성을 위해 둘 다 둔다.

완료 조건:

- 기존 진행 데이터는 해당 코스의 `v1`에 귀속된다.
- 신규 학습자가 코스를 시작하면 최신 published 버전에 귀속된다.
- 진행률과 다음 레슨 계산은 학습자의 진행 버전을 기준으로 동작한다.

### 4단계: 버전 인식 읽기 경로

목표는 콘텐츠 조회와 학습 진행 조회가 서로 다른 버전 기준을 명확히 따르게 하는 것이다.

API 정책:

- 공개 `GET /courses`는 최신 published 버전 요약을 반환한다.
- 공개 `GET /courses/:courseId`는 최신 published 버전 상세를 반환한다.
- 인증된 `GET /courses/:courseId/progress`는 학습자의 진행 버전을 기준으로 진행률을 계산한다.
- 인증된 레슨 진행 저장은 레슨이 학습자의 진행 버전에 포함되는지 검증한다.
- 레슨 상세 조회는 기존 URL 호환성을 유지하되, 진행 저장과 완료 처리에서 버전 일관성을 보장한다.

완료 조건:

- 최신 버전에 새 레슨이 추가되어도 기존 학습자의 완료율이 갑자기 낮아지지 않는다.
- 기존 학습자의 다음 레슨은 기존 버전 구조에서 계산된다.
- 신규 학습자는 최신 published 구조로 시작한다.

### 5단계: 아카이빙과 상태 정책

목표는 삭제를 상태 전환으로 대체하는 것이다.

포함 범위:

- 챕터와 레슨 노드 상태 추가
- 신규 학습자 경로에서 archived 노드 숨김
- 기존 학습자 진행 버전에서는 완료 성취 보존
- 관리자 조회에서 archived/deprecated 상태 표시

완료 조건:

- archived 레슨은 신규 published 경로에 노출되지 않는다.
- 이미 완료한 archived 레슨은 학습자의 완료 카운트에서 사라지지 않는다.
- 실제 delete API는 제공하지 않는다.

### 6단계: 관리자 draft/published 발행 워크플로우

목표는 관리자가 published 콘텐츠를 직접 바꾸지 않고 draft를 통해 새 버전을 발행하게 하는 것이다.

관리자 API 후보:

```text
POST /courses/:courseId/curriculum-versions
PATCH /curriculum-versions/:versionId
POST /curriculum-versions/:versionId/publish
GET /courses/:courseId/curriculum-versions
GET /curriculum-versions/:versionId
```

정책:

- published 버전의 구조는 직접 수정하지 않는다.
- draft 버전은 관리자만 볼 수 있다.
- 구조 변경은 draft에서 작업한 뒤 publish해야 신규 학습자에게 적용된다.
- 마이너 편집은 별도 정책에 따라 같은 버전에 반영할 수 있지만, 이 경우에도 감사 가능한 변경 기록을 남긴다.

완료 조건:

- 관리자는 현재 published 버전에서 draft를 생성할 수 있다.
- draft를 발행하면 해당 코스의 최신 published 버전이 된다.
- 기존 학습자의 진행 버전은 자동으로 바뀌지 않는다.

### 7단계: 마이그레이션 맵

목표는 구조 변경이 있을 때 기존 진도를 새 버전으로 이식할 수 있는 명시적 매핑을 제공하는 것이다.

추가 후보 테이블:

```text
curriculum_version_migrations
  - id
  - from_version_id
  - to_version_id
  - status
  - created_at

lesson_migration_mappings
  - id
  - migration_id
  - from_lesson_id
  - to_lesson_id
  - mapping_type
```

매핑 타입:

```ts
type LessonMigrationMappingType = "equivalent" | "split" | "merged" | "removed"
```

정책:

- 매핑이 없는 구조 변경은 자동 마이그레이션하지 않는다.
- `equivalent`는 완료 상태를 그대로 이전할 수 있다.
- `split`은 관리자가 어느 새 레슨까지 완료로 볼지 명시해야 한다.
- `merged`는 관련 레슨 완료 여부를 기준으로 보수적으로 처리한다.
- `removed`는 완료 성취는 보존하되 새 경로의 완료율 계산에서 어떻게 반영할지 정책을 명시한다.

완료 조건:

- 관리자 지정 맵을 기준으로만 진행 이전이 가능하다.
- 마이그레이션 결과는 재실행해도 같은 결과를 내야 한다.
- 실패한 마이그레이션은 부분 완료 상태를 숨기지 않고 관측 가능해야 한다.

### 8단계: 학습자 업그레이드 UX와 공지

목표는 구조 변경을 학습자에게 갑자기 강제하지 않고 선택지와 맥락을 제공하는 것이다.

학습자 선택지:

- 새 커리큘럼으로 업그레이드
- 지금 하던 버전을 계속 학습
- 나중에 결정

API 후보:

```text
GET /courses/:courseId/curriculum-upgrade
POST /courses/:courseId/curriculum-upgrade
POST /courses/:courseId/curriculum-upgrade/dismiss
```

완료 조건:

- 학습자는 명시적으로 선택하기 전까지 현재 버전을 유지한다.
- 업그레이드 시 마이그레이션 맵이 적용되고 결과를 확인할 수 있다.
- 나중에 결정을 선택하면 학습 흐름이 막히지 않는다.
- 새 버전 공지는 변경 이유와 기대 효과를 짧고 구체적으로 설명한다.

## 서비스와 API 경계

`packages/core`는 콘텐츠 버전 정책의 중심 경계가 된다.

- 콘텐츠 DTO는 필요한 경우 버전 ID를 내부 모델에 추가하되, 공개 API 응답 변경은 단계별로 최소화한다.
- 학습 서비스는 코스 시작 시 최신 published 버전을 선택한다.
- 진행 조회와 완료 처리는 학습자의 버전과 레슨 포함 여부를 검증한다.
- 관리자 서비스는 draft/published 발행 정책을 담당한다.

`packages/db`는 Drizzle schema, migration SQL, repository 구현을 담당한다.

- 기존 콘텐츠 seed는 `v1` published 버전을 생성하도록 확장한다.
- repository는 최신 published 조회와 특정 버전 조회를 분리한다.
- 학습 진행 repository는 버전 ID를 저장하고 조회한다.

`apps/api`는 학습자 API 경계를 유지한다.

- 공개 콘텐츠 조회는 최신 published 기준을 따른다.
- 인증된 진행 API는 사용자의 진행 버전을 따른다.
- 임의 버전 전환은 업그레이드 API를 통하지 않고 수행하지 않는다.

`apps/admin-api`와 `apps/admin`은 관리자 운영 경계를 담당한다.

- 초기에는 버전 조회와 상태 표시부터 시작한다.
- 편집과 발행은 draft/published 단계에서 추가한다.
- 실제 삭제 기능은 제공하지 않는다.

## 테스트 전략

각 단계는 좁은 테스트로 완료 조건을 검증한다.

- Core service 테스트
  - 최신 published 선택
  - 기존 진행 버전 유지
  - 완료 성취 보존
  - 잘못된 버전·레슨 조합 거절
- DB repository 테스트
  - `v1` 마이그레이션
  - 버전별 챕터·레슨 정렬
  - archived 노드 필터링
  - 진행 버전 저장
- API route 테스트
  - 공개 콘텐츠 조회 호환성
  - 인증 진행 조회의 버전 기준 계산
  - 관리자 draft/published API 인증과 정책
- UI 테스트
  - 관리자 버전 목록과 상태 표시
  - 학습자 업그레이드 안내와 선택 흐름
- 회귀 테스트
  - 기존 코스 목록, 코스 상세, 레슨 상세, 레슨 완료 경로가 깨지지 않는다.

## 위험과 완화

### 기존 진행 데이터 마이그레이션

기존 `course_progress`와 `lesson_progress`는 버전 정보가 없다. 2단계와 3단계에서 모든 기존 진행을 `v1`에 귀속시키는 마이그레이션이 필요하다.

완화:

- 코스별 기본 `v1`을 먼저 생성한다.
- 진행 데이터 업데이트는 deterministic하게 수행한다.
- 마이그레이션 테스트에서 기존 완료 카운트가 유지되는지 검증한다.

### API 응답 호환성

공개 콘텐츠 API 응답에 버전 정보를 바로 노출하면 프론트엔드 변경 범위가 커질 수 있다.

완화:

- 내부 repository와 service에서 먼저 버전을 인식한다.
- 외부 DTO 확장은 필요한 단계에서만 추가한다.
- 기존 응답 형태는 가능한 한 유지한다.

### 본문 콘텐츠 스냅샷 범위

레슨 본문과 step을 완전히 버전별로 복제하면 데이터 모델이 커진다. 반대로 본문을 공유하면 과거 버전의 레슨 내용도 최신 본문으로 바뀔 수 있다.

완화:

- 1차에서는 구조 버전을 우선한다.
- `minor-edit`와 `additive`는 같은 레슨 본문에 반영 가능하다는 정책을 명시한다.
- major revision에서 본문 불변성이 필요해지면 lesson/step snapshot 확장을 별도 단계로 검토한다.

### 관리자 편집 UX 복잡도

draft/published, 변경 유형, 마이그레이션 맵을 한 화면에 모두 넣으면 운영자가 이해하기 어렵다.

완화:

- 버전 목록과 상태 표시를 먼저 만든다.
- draft 편집과 publish는 별도 흐름으로 둔다.
- 마이그레이션 맵은 major revision 단계에서만 요구한다.

## 승인된 결정

- 전체 작업은 단일 구현이 아니라 단계형 로드맵으로 고정한다.
- 관리자 CMS보다 커리큘럼 버전 경계를 먼저 구현한다.
- 기존 콘텐츠는 코스별 `v1` published 버전으로 시작한다.
- 신규 학습자는 최신 published 버전으로 시작한다.
- 기존 학습자는 명시적 업그레이드 전까지 자신의 진행 버전을 유지한다.
- 삭제는 실제 삭제가 아니라 `deprecated` 또는 `archived` 상태 전환으로 처리한다.
- 학습자가 이미 완료한 성취는 구조 변경으로 사라지지 않는다.
