# 테스트 인프라·설정 감사

대상은 개별 테스트 케이스가 아니라 스위트 전체를 지탱하는 설정·지원 코드다. 케이스 수준 소견은 같은 디렉터리의 `api.md`·`web.md`·`admin.md`·`modules.md`·`infra-shared.md`가 소유한다.

## 요약

가장 시급한 3가지.

1. **turbo `test` cache가 migration SQL을 보지 못해 통합 테스트가 cached-green이 될 수 있다** (치명). `packages/infra/db/src/test-support/application-migration.ts:11-20`이 `apps/api/drizzle/*.sql`을 상대 URL로 읽지만, `turbo.json:30`의 `inputs`는 `$TURBO_DEFAULT$`(패키지 내부 파일)뿐이고 `@workspace/db`는 `apps/api`에 의존하지 않는다(`packages/infra/db/package.json:25-27`). baseline schema를 고쳐도 `@workspace/learning#test` 등 모듈 통합 테스트는 cache를 재생해 초록으로 통과한다.
2. **스위트 wall time의 대부분이 테스트가 아니라 러너 기동·환경 생성이다** (높음). 실측(캐시된 `turbo-test.log`): `@workspace/http-client`는 총 4.03s 중 실제 테스트가 213ms, `@workspace/learning`은 5.74s 중 576ms다. 14개 패키지가 각자 root `vitest.workspace.ts`를 다시 로드하는 별도 프로세스를 띄우고(`packages/modules/learning/package.json:18` 등), `turbo.json:29`의 `^test`가 이 프로세스들을 의존성 그래프 순서로 직렬화하며, web·admin은 `maxWorkers: 2`로 병렬성을 스스로 묶어 각각 38.02s·36.89s가 걸린다(`apps/web/vitest.config.ts:54`, `apps/admin/vitest.config.ts:37`).
3. **테스트 지원 코드가 프로덕션 공개 표면으로 나가 있는데 이를 막는 검사가 없다** (높음). 5개 모듈 전부 `./test-fixtures`를 `exports`에 선언하고(`packages/modules/*/package.json:13-14`) `@workspace/db`도 `./test-support/*`를 공개한다(`packages/infra/db/package.json:16-17`). dependency-cruiser의 `external-consumers-use-module-public-exports`는 공개 export를 허용 대상으로 계산하므로 프로덕션 소스가 fixture를 import해도 통과하고, oxlint의 `@/test/*` 금지 규칙은 `apps/web/src/**`에만 있다(`.oxlintrc.json:251`).

명시적 답변.

- **`node --test`는 쓰이지 않는다.** `scripts/oxlint/workspace-rules.node-test.mjs`는 파일명만 `node-test`이고 `node:test`를 import하지 않는다. oxlint의 `RuleTester`(`:3`)가 자체적으로 케이스를 돌리고, `:49`의 `assert.ok(true)`는 아무것도 검증하지 않는 잔여 코드다. 파일명을 `workspace-rules.rule-cases.mjs`처럼 실제 실행 방식에 맞추고 `:1,49`를 제거해야 한다.
- **Storybook은 `test-runner`가 아니라 Vitest browser mode**다(`@storybook/addon-vitest` + `@vitest/browser-playwright`). `apps/storybook`에는 `test` script가 없어 `turbo test`에 포함되지 않고 `main-e2e`에서만 돈다.
- **`vitest.workspace.ts`는 18개 project를 소유**한다(config 참조 4개 `:11-14` + 인라인 node project 14개 `:15-45`). 그런데 어떤 명령도 이 파일을 전체 실행하지 않고, 앞의 4개는 `--project`로 선택되지도 않는다(4개 앱은 각자 config를 직접 실행). 즉 매 패키지 테스트마다 쓰이지 않는 config 4개를 함께 resolve한다.
- **통합 권고 순서**: (1) `turbo.json:29`의 `^test` 제거, (2) 14개 패키지 script를 root 단일 실행(`vitest run --config vitest.workspace.ts`)으로 대체하고 패키지별 script는 `--project` 필터만 남기는 개발자 편의용으로 격하, (3) `bun test ./scripts`를 root workspace project로 흡수.

## 3. setup 파일 비대칭과 mock 누출 위험

현재 상태.

| workspace            | setupFiles                                         | restoreMocks   | globals        | 콘솔 gate |
| -------------------- | -------------------------------------------------- | -------------- | -------------- | --------- |
| `apps/api`           | 없음                                               | 없음           | 없음           | 없음      |
| `apps/web`           | `vitest.setup.ts` (jest-dom + `cleanup`)           | 없음           | 없음           | 없음      |
| `apps/admin`         | `vitest.setup.ts` (jest-dom + `cleanup` + harness) | 없음           | 없음           | 있음      |
| `packages/shared/ui` | `vitest.setup.ts` (jest-dom + `cleanup`)           | `true` (`:18`) | `true` (`:16`) | 없음      |

**판정: web·admin의 `restoreMocks` 부재는 실제 누출 원인이 아니다.** 코드로 확인한 결과 `apps/web`·`apps/admin`의 어떤 테스트도 `vi.spyOn`을 쓰지 않는다(grep `spyOn|setSystemTime|useFakeTimers` 전체 결과가 `apps/web/src/features/lesson-session/hooks/use-lesson-draft-sync.test.tsx:29`의 `vi.useFakeTimers()` 하나뿐이고, 그 파일은 `:42-44`에서 `vi.useRealTimers()`로 복원한다). `restoreMocks`는 `vi.spyOn` 스파이만 복원하므로 지금 켜도 no-op이다.

**실제 누출 벡터는 `vi.stubGlobal`이고 이것은 `restoreMocks`가 아니라 `unstubGlobals`가 담당한다.** 사용처 4곳 중 3곳은 손으로 `vi.unstubAllGlobals()`를 호출한다(`apps/admin/src/features/authentication/ui/admin-auth-client.test.ts:9-11`, `apps/web/src/features/authentication/api/auth-client.test.ts:10-12`, `apps/web/src/test/learner-api-ui.integration.test.tsx:70-73`). **`apps/web/src/server/http/learner-api-client.test.ts:30`은 전역 `fetch`를 stub한 뒤 복원하지 않는다** — 같은 파일의 두 번째 테스트(`:48`)가 fetch를 쓰지 않아 지금은 초록이지만, 파일 내 실행 순서에 의존하는 상태 누출이다(C-2). Vitest 기본 `isolate`가 파일 단위 격리를 주므로 파일 간 전파는 없다. 심각도 **중간**.

조치.

1. 4개 config에 `unstubEnvs: true`, `unstubGlobals: true`를 공통으로 켠다(§2 I3 factory에 포함). 그러면 3곳의 수동 `unstubAllGlobals()`와 `apps/admin/src/server/auth/get-admin-session-token.test.ts:14`의 `unstubAllEnvs()`도 함께 지울 수 있다.
2. `restoreMocks`는 `packages/shared/ui`에서만 값을 한다(`ai-feedback-answer.test.tsx:81`의 `vi.spyOn(Date, "now")`). 4개 config에 일괄로 켜는 것 자체는 무해하고 대칭성 이득이 있으므로 함께 켠다. 켠 뒤 `ai-feedback-answer.test.tsx:19-21`의 수동 `vi.restoreAllMocks()`는 삭제한다.
3. `packages/shared/ui/vitest.config.ts:16`의 `globals: true`는 **죽은 설정**이다. 6개 테스트 파일 전부 `from "vitest"`로 명시 import한다. 삭제한다.
4. `apps/api`에 setupFiles가 없는 것은 정상이다(node 환경, DOM cleanup 불필요). 단 §4의 콘솔 gate를 도입한다면 api도 대상이다.

## 4. console failure harness

`apps/admin/src/shared/test/console-failure-harness.ts`는 `beforeEach`에서 `console.error`/`console.warn`을 throw하는 함수로 교체하고 `afterEach`에서 모듈 로드 시점의 원본으로 복원한다(`:11-21`). `apps/admin/vitest.setup.ts:7`에서만 설치되고 web·shared/ui에는 없다.

- **비대칭이 의도된 것인지**: 근거가 없다. 커밋 의도를 설명하는 주석도, testing.md의 서술도 없다. testing.md는 브라우저 smoke에 대해서만 "각 페이지의 console warning·error와 page error는 allowlist 없이 실패로 처리한다"고 쓰고(`docs/engineering/testing.md:53`) 단위·UI 테스트 계층에는 아무 규정이 없다. 즉 admin에만 있는 것은 **문서화되지 않은 우발적 비대칭**이다.
- **web에도 필요한가**: 필요하다. web은 admin과 같은 React·jsdom·Testing Library 조합이고 오류 상태·error boundary 테스트를 갖는다. 다만 지금 바로 켜면 React가 내는 `act` 경고나 error boundary 로그로 기존 테스트가 깨질 수 있으므로 무조건 도입은 위험하다. 조사한 범위에서 web·shared/ui 테스트 중 `console.*`을 언급하는 파일은 하나도 없어(grep 결과 0건) 의도적으로 콘솔 출력을 기대하는 테스트는 없다.
- **조치**: harness를 `apps/admin/src/shared/test/`에서 공유 위치(`packages/shared/ui`의 test-support 또는 신설 `packages/config/vitest-preset`)로 올리고 web·shared/ui·api 4곳 setup에서 설치한다. 지금 위치는 app-local `@/shared/test/*` 경로라 다른 workspace가 재사용할 수 없다(D-6는 위치를 지키지만 공유는 불가능하다).
- **harness 자체 테스트(`console-failure-harness.test.ts`, 13줄) 판정**: **유효하지만 계약이 과하다.** 이 테스트는 `installConsoleFailureHarness()`를 직접 호출하지 않고 `vitest.setup.ts`가 설치한 전역 상태를 관찰한다. 따라서 누군가 `apps/admin/vitest.setup.ts:7`에서 설치 호출을 지우면 이 테스트만 빨개진다 — lint·타입으로는 잡을 수 없는 실제 회귀 가드이므로 D-14 위반이 아니다. 문제는 `:8-9`가 한국어 메시지 전문(`예상하지 않은 console.error: 콘솔 실패 장치 확인`)을 고정한다는 점이다. testing.md는 source 문자열을 회귀 계약으로 삼지 말라고 규정한다(`docs/engineering/testing.md:14`). `toThrow(/console\.error/)` 수준으로 낮춘다. 심각도 **낮음**.
- 덧붙여 harness는 `beforeEach`/`afterEach`를 setup 파일 top-level에서 등록하므로 hook 등록 순서상 `cleanup()`(`vitest.setup.ts:9-11`)이 먼저 실행되고 console 복원이 나중에 실행된다. 즉 unmount 중 발생하는 React 경고도 실패로 잡힌다. 의도된 것으로 보이나 근거 주석이 없다.

## 8. knip/oxlint 사각지대

**knip은 통과한다**(`bun run check:knip` → exit 0, `--treat-config-hints-as-errors` 포함). 그러나 다음을 구조적으로 못 본다.

1. **모듈 `./test-fixtures`의 미사용 export** (중간, C-13). `packages/{config,infra,modules,shared}/*` workspace 설정에는 `includeEntryExports`가 없고(`knip.json:44-46`) 기본값은 false다. `./test-fixtures`는 package.json `exports`로 선언돼 entry로 취급되므로 그 파일의 export는 사용 여부 검사에서 아예 빠진다. `includeEntryExports: true`가 켜진 workspace는 `packages/infra/http-client` 하나뿐이다(`knip.json:53`). 실증: sibling 감사가 `learning/src/test/fixtures/lesson-step-presentation-cases.ts`의 `withFutureSecret`이 index로 공개됐지만 소비자가 없다고 보고했는데(`modules.md` F4), knip은 이를 잡지 못했다.
2. **`*.typecheck.ts` 전면 제외** (낮음). `knip.json:3`이 `packages/**/src/**/*.typecheck.{ts,tsx}`를 `ignoreFiles`로 뺀다. `packages/shared/types/src/ids.typecheck.ts`는 아무 검사도 받지 않는다. 의도된 예외지만 파일이 늘어나면 사각지대도 늘어난다.
3. **앱 root의 테스트 설정 파일이 project 밖** (낮음). `apps/*`의 `project`는 `src/**/*.{css,ts,tsx}`뿐이라(`knip.json:30`) `vitest.config.ts`·`vitest.setup.ts`가 분석 대상이 아니다.
4. **테스트 파일을 entry로 선언** (관찰). `knip.json:28,36`이 `src/**/*.{test,spec}.*`를 entry로 둔다. 이는 fixture 파일의 사용 여부는 정상 추적하게 하지만(그래서 `apps/web/src/test/learner-api-fixtures.ts`의 미사용 export는 잡힌다), 테스트 파일 자체가 죽었는지는 판정 불가로 만든다.

**oxlint 사각지대.**

1. **D-6 경계 규칙이 `apps/web`에만 있다** (중간, D-6). `.oxlintrc.json:251-270`이 `apps/web/src/**`에서 `@/test/*`와 상대 `../test/*` import를 금지하고 `:273-275`가 테스트 파일만 예외로 푼다. `apps/admin`에는 같은 규칙이 없는데, admin에도 `src/test/admin-api-fixtures.ts`와 `src/shared/test/console-failure-harness.ts`가 있다. 같은 override의 `files` 배열에 admin `src` glob을 추가하면 끝난다.
2. **workspace 간 test 지원 import를 아무도 막지 않는다** (높음, D-6). `@workspace/content/test-fixtures`, `@workspace/db/test-support/application-migration` 같은 경로는 production `exports`로 선언된 공개 subpath다. dependency-cruiser의 `external-consumers-use-module-public-exports`는 공개 export를 **허용 목록으로 계산**하므로(`dependency-cruiser.config.mjs:150`의 `readModulePublicTargetPattern`이 `exports`를 읽어 패턴을 만든다) 프로덕션 소스가 fixture를 import해도 error가 아니다. 현재 소비자는 테스트뿐이지만(grep 확인: `apps/api/src/privacy/deleted-learner-purge.integration.test.ts`, 모듈 테스트, `operations`) 규칙이 아니라 관행에 의존한다. dependency-cruiser에 "`test-fixtures`·`test-support` 경로는 `*.test.ts`와 `src/test*/**`에서만 import 가능" 규칙을 추가한다.
3. **E2E 전용 코드가 `apps/api/src/scripts/`에 있다** (중간, D-6). `setup-e2e-database.ts`, `setup-e2e-content-database.ts`, `start-e2e-api.ts`, `assert-e2e-published-content-immutable.ts` 4개는 E2E만 쓰는 지원 코드인데 production `src/scripts/`에 있다. 같은 앱에 `src/test-support/`가 이미 있다(`learner-app-fixture.ts`, `unified-api-shutdown-process.ts`). 옮기면 §6의 topology 중복도 함께 해결할 실마리가 생긴다. knip은 `src/scripts/*.ts!`를 강제 entry로 선언해(`knip.json:34`) 이 4개가 프로덕션 entry라고 단언한다.
4. **테스트 파일을 완화하는 override는 없다**(확인 완료). `no-console: "error"`(`.oxlintrc.json:109`)와 `typescript/no-explicit-any`가 테스트 파일에도 그대로 적용된다. 좋은 상태다.

- **web·admin의 `maxWorkers: 2`는 상태 공유 때문이 아니다.** 두 앱의 테스트는 `vi.mock`/`vi.stubGlobal`을 파일 안에서만 쓰고 파일 간 공유 상태가 없다(§3). Vitest 기본 `isolate`가 파일 단위 격리를 준다. 그런데 web은 35파일마다 jsdom 환경을 새로 만들어 environment 누적 35.35s를 worker 2개로 나눠 쓴다 — wall time 38s의 지배 요인이 이것이다. `maxWorkers` 상한을 올리면 거의 선형으로 줄어든다. 두 config에 이 값의 근거 주석이 없어(`apps/web/vitest.config.ts:54`, `apps/admin/vitest.config.ts:37`) 왜 묶었는지 코드에서 알 수 없다. **정당한 근거가 확인되지 않는 제약이므로 제거 후 재측정을 권고한다** (중간).
- **패키지 단위 프로세스 파편화가 두 번째 요인이다.** `@workspace/http-client`는 실제 테스트 0.21s를 위해 4.03s를 쓴다(비율 19:1). 14개 패키지가 각자 root `vitest.workspace.ts`(18 project 전체)를 resolve하고 자기 프로세스를 띄운다. root에서 한 번 실행하면 transform·import·worker pool을 공유한다.
- **`turbo.json:29`의 `^test`가 셋을 곱한다** (높음, A-11). `@workspace/learning#test`는 `@workspace/content#test`·`@workspace/db#test`·`@workspace/contracts#test`가 끝나기를 기다린다. 테스트는 서로의 산출물을 소비하지 않으므로 이 의존은 근거가 없고, `--concurrency=50%`(`package.json:96`)로 넓힌 병렬성을 그래프 깊이만큼 되돌린다.
- **Playwright의 `workers: 1`·`fullyParallel: false`는 C-2 때문에 강제된 것이 맞다** (유지 권고). 한 번의 실행이 단일 SQLite fixture 파일(`scripts/run-e2e.ts:8`)과 단일 서버 조립(`playwright.config.ts:58`)을 모든 spec이 공유한다. `e2e/pr-smoke.spec.ts:9`가 `test.describe.configure({ mode: "serial" })`를 추가로 선언하는 것도 같은 이유다. 병렬화하려면 worker별 DB·서버·port가 필요한데, 그것은 fixture 준비 비용을 worker 수만큼 곱한다. 현재 선택이 합리적이다. `globalTimeout: 600_000`(`:29`)은 flaky 은폐가 아니라 hung 실행 상한이고, `timeout: 30_000`(`:48`)도 확대된 값이 아니다. **`retries: 0`(`:35`)과 `failOnFlakyTests: isCi`(`:25`)로 D-10을 정면으로 지킨다.** C-3 해당 없음.
- **lefthook pre-commit이 테스트를 돌리지 않는 것은 적절하다** (`lefthook.yml:3-13`은 staged 파일 대상 oxfmt·oxlint만 실행). 위 측정치를 합치면 전체 스위트는 100초를 넘고 캐시가 없으면 더 길다. commit 훅에 넣으면 C-11(개발자가 훅을 우회)을 만든다. 대신 `bun run test`가 사람이 자주 누를 만큼 빨라져야 하고, 그 개선 여지가 위 세 항목이다. 다만 pre-commit이 staged 파일만 lint하므로 다른 파일을 깨뜨리는 변경은 CI까지 통과한다 — 의도된 trade-off로 보이며 이 감사는 문제로 보지 않는다.
- 곁가지: `apps/api/src/main.test.ts`의 "factory를 import해도 process와 server를 시작하지 않는다"가 단독으로 7.46s를 쓴다(api 전체 wall 9.52s의 대부분). `src/lifecycle/server-lifecycle.process.test.ts`에는 skip 1건이 있다. 케이스 수준 판단은 `api.md`로 넘긴다.
