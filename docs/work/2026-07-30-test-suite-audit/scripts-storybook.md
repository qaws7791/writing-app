# scripts · Storybook 테스트 감사

## 요약

- 검토 파일 수: scripts 6/6, storybook 35/35 (총 41/41)
- 삭제 권고 19건 · 수정 권고 23건 · 개별 지적 없음 4개 파일 (`ui/accordion`, `ui/button`, `ui/select`, `ui/surface`)
- 실행 경로는 추측하지 않고 격리 실험으로 확인했다. bun의 테스트 파일 탐색은 `.test`·`_test_`·`.spec`·`_spec_`만 인정하므로 `admin-dev-lifecycle.smoke.ts`와 `workspace-rules.node-test.mjs`는 `bun test ./scripts`에 **잡히지 않는다**(임시 디렉터리에 동일 이름 규칙 파일을 만들어 확인, 실험 파일은 삭제했다).
- 삭제된 resource·chat 기능의 story·fixture 잔존(D-10 마지막 문장)은 **없다**. `apps/storybook/src` 전체에서 `chat|conversation|resource` grep 결과는 `dropdown-menu.stories.tsx:11,192`의 `MessageSquare` 아이콘과 `textarea.stories.tsx:70`의 "메시지" 라벨뿐이며 제거된 기능의 fixture가 아니다.

가장 시급한 3가지

1. **`scripts/production-readiness.test.ts:125-208`이 Ansible playbook을 자체 parser로 재해석한다.** `Bun.YAML.parse`로 `infra/ansible/playbooks/deploy.yaml`을 읽고 Jinja 조건 문자열(`to_datetime(`, `total_seconds() <= 2678400`, `search(`)의 부분 일치와 task 배열 index 순서를 단정한다. `docs/engineering/testing.md:116`이 "배포 설정은 자체 parser로 재해석하지 않고 Compose·Caddy·Ansible과 실제 container가 직접 읽게 한다"고 금지한 패턴이다. 게다가 이 단정이 통과해도 **Ansible이 실제로 그 gate에서 멈추는지는 어디에서도 검증되지 않는다**. `check:deployment-ansible`은 lint·syntax만, `test:deployment-bootstrap`은 bootstrap·maintenance playbook만 실행한다.
2. **Storybook 범위를 정하는 두 권위 문서가 서로 충돌한다.** `docs/design/storybook.md:33`은 "제품 화면 조합은 primitive story와 분리해 Pattern 또는 Recipe에 둔다"며 화면 조합을 **허용**하고, `docs/engineering/testing.md:40`은 "앱 전용 화면과 도메인 흐름을 옮기지 않으며"라고 **금지**한다. lesson 10개 + `admin-patterns` + `course-management` + `checklist`, 총 13개 파일 1,421줄의 존폐가 이 충돌에 걸려 있다. `docs/authority-map.md:66`은 이 상황에서 문서를 임의로 맞추지 말고 소유권 결정을 먼저 요청하라고 규정한다.
3. **`ai-feedback-answer.stories.tsx`의 interaction test 5개는 단정이 하나도 없다.** `play`가 `canvasElement.querySelector("button")?.click()`만 하고 끝난다(`:149-152, 162-165, 175-178, 188-191, 201-204`). 버튼이 없어도 optional chaining으로 통과하므로 실패할 수 없다. 같은 4개 결과 상태(성공·retryable·quota·limit)를 `packages/shared/ui/src/components/lesson/ai-feedback-answer.test.tsx:23-137`이 단정과 함께 이미 검증한다. 여기에 `:32-38`의 `setTimeout(…, 60_000)` mock이 teardown 이후까지 살아 있는 timer를 남긴다.

## 러너 이질성 평가

현재 이 저장소는 다섯 가지 실행 방식을 동시에 운영한다.

1. **Vitest** — workspace unit·integration. 앱 3개 전용 config + `packages/shared/ui` config + `vitest.workspace.ts`의 project 14개.
2. **bun 내장 test** — `scripts/*.test.ts` 4개(`ci:tests:repository`)와 `admin-dev-lifecycle.smoke.ts`(전용 명령).
3. **러너 없는 plain node** — `scripts/oxlint/workspace-rules.node-test.mjs`.
4. **Vitest browser + Playwright provider** — Storybook story 35개(`vitest.storybook.config.ts`).
5. **Playwright** — E2E(`playwright.config.ts`).

확인된 문제:

- **`.node-test.mjs`는 러너가 아니다.** 파일명이 `node --test`를 암시하지만 `node:test`를 import하지 않는다. `oxlint/plugins-dev`의 `RuleTester`가 전역 `describe`/`it`가 없으면 자체 fallback으로 케이스를 즉시 실행하고(`plugins-dev.js:151,163`) 불일치 시 `AssertionError`를 던진다. 잘못된 기대를 심은 격리 probe로 실제 실패를 확인했다(`AssertionError … 0 !== 1`, exit 1). 즉 단정에 힘은 있다. 다만 성공 시 출력이 한 줄도 없어 몇 개 케이스가 통과했는지 알 수 없다(A-9, B-7).
- **이 파일을 `bun test`로 통합할 수는 없다.** `bun scripts/oxlint/workspace-rules.node-test.mjs`를 실행하면 `RuleTester is not supported on … other runtimes`로 즉시 실패한다(`plugins-dev.js:75`). RuleTester는 Node.js ≥ 22의 raw transfer 바인딩을 요구한다. **따라서 현재의 러너 분리는 우연이 아니라 도구 제약에 따른 정당한 선택이다.** 통합을 원하면 Vitest(Node pool) project로 옮기는 것만이 가능한 경로이며, RuleTester가 전역 `describe`/`it`를 사용하므로 케이스별 보고까지 얻는다.
- **파일 탐색 규칙이 이중화되어 "아무 러너도 잡지 않는 테스트"가 가능하다.** bun은 파일 **이름 규칙**으로, Vitest는 config **경로 include**로 대상을 정한다. `beta.smoke.ts`·`delta.node-test.mjs`가 bun에 잡히지 않는 것을 실험으로 확인했다. 지금은 `admin-dev-lifecycle.smoke.ts`(전용 명령)와 `workspace-rules.node-test.mjs`(전용 script)가 각자 명령을 가져 실행되지만, 그 script가 사라지면 조용히 실행되지 않는다. 실제로 `admin-dev-lifecycle.smoke.ts`는 **CI 어디에서도 실행되지 않는다**(M9).
- **assertion API와 런타임 API가 파일 단위로 갈린다.** `production-readiness.test.ts:126-137`은 `Bun.YAML.parse`와 `Bun.file`을, `admin-dev-lifecycle.smoke.ts`는 `Bun.spawn`·`Bun.sleep`을 쓴다. 이 파일들은 Vitest로 옮길 수 없다. 반대로 `csp-policy.test.ts`는 bun 전용 API를 쓰지 않으므로 옮길 수 있다. 어느 파일이 어느 러너에 묶여 있는지가 코드에서 드러나지 않는다.
- **패키지 경계와 테스트 위치가 어긋난 사례가 하나 있다.** `csp-policy.test.ts`는 `@workspace/nextjs-config`를 검증하는데, 그 패키지에는 `test` script도 Vitest project도 없다(`packages/config/nextjs-config/package.json:13-16`). 저장소 계약 suite가 패키지 단위 테스트를 대신 떠맡고 있다.
- **Storybook 러너는 나머지와 gate가 분리되어 있다.** `vitest.storybook.config.ts`는 루트 `vitest.workspace.ts`에 편입되지 않고, `apps/storybook`에 `test` script가 없어 `turbo test`에도 없다. 결과적으로 PR에서 실행되지 않는다(M22).

권고 순서:

1. `csp-policy.test.ts`를 `@workspace/nextjs-config`의 Vitest project로 이동한다(M3). bun suite는 저장소 계약(정책·배포 증거)만 남긴다.
2. `workspace-rules.node-test.mjs`는 **Node에 남긴다.** 보고 품질이 필요하면 Vitest Node project로 옮기고, 그렇지 않으면 현행 유지하되 파일 헤더에 "bun에서 실행 불가"를 한 줄로 명시한다.
3. bun suite에 남는 파일은 이름 규칙(`*.test.ts`)을 반드시 지키게 하고, 전용 명령으로만 실행하는 파일(`*.smoke.ts`)은 그 명령이 CI나 주기 실행에 연결되어 있는지를 `check-workflow-scripts` 수준의 정적 검사로 보장한다.
4. Storybook은 interaction·a11y가 있는 부분집합을 PR gate로 승격한다(M22).
