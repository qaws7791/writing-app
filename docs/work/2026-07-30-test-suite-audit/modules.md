# packages/modules 테스트 감사

## 요약

- 검토 파일 수: 42/42 (learning 14 · content 10 · identity 6 · operations 6 · ai-feedback 6). 모듈별 `src/test/fixtures/**` 11개 파일도 함께 읽었다.
- 삭제 권고 20건 · 수정 권고 32건(표) + 낮은 심각도 8건(본문 기록) · 문제 없음 12건
- 가장 시급한 3가지
  1. **죽은 schema fixture가 프로덕션 schema를 복제한다.** `runCurrentTestMigration`이 실행하는 baseline이 이미 `ai_feedback_attempts`의 전체 column과 `ai_feedback_global_daily_counters`·`ai_feedback_user_daily_counters`·`learner_step_drafts`를 만든다(`apps/api/drizzle/0000-current-schema-baseline.sql:13,16,18`, `:38`, `:46`, `:357`). 그런데 `ai-feedback/src/test/fixtures/purge-test-schema.ts:4-55` 전체와 `learning-drizzle-repository.test.ts:702-736`이 같은 대상을 `ALTER TABLE` 가드와 `CREATE TABLE IF NOT EXISTS`로 다시 만든다. 전부 no-op으로 실행되지 않는 죽은 코드이고, fixture 쪽 정의에는 프로덕션 CHECK·FK가 빠져 있어 migration이 갈라지는 순간 조용히 약한 schema로 테스트가 통과한다(D-3).
  2. **`operations-reporting-sqlite-repository.test.ts`가 검증 대상 view를 테스트 안에서 재구현한다.** `:116-155`가 `user`·`learner_profiles`·`ai_feedback_attempts` table과 `identity_reporting_learners`·`ai_feedback_reporting_attempts` view를 손으로 만든다. "삭제된 학습자를 제외한다"는 이 파일의 핵심 주장은 프로덕션 view(`apps/api/drizzle/0001-reporting-views.sql`)가 아니라 테스트가 쓴 view를 검증한다. 같은 모듈의 sibling `operations-reporting-metrics-sqlite-repository.test.ts:10-17`이 실제 migration과 `test-fixtures` 빌더를 쓰므로 교정 경로가 이미 존재한다(D-3, C-10).
  3. **모듈이 자기 fixture를 쓰지 않아 같은 시드를 4곳에서 다시 짠다.** `aPublishedCourse`·`aLearner`·`aLearnerWithProgress`는 `apps/api`의 통합 테스트만 소비하고(`apps/api/src/privacy/deleted-learner-purge.integration.test.ts:5-11`), 정작 모듈 자기 통합 테스트는 같은 published course·학습자 시드를 인라인 SQL로 복제한다(`learning-drizzle-repository.test.ts:737-771`, `ai-feedback-drizzle-repository.test.ts:674-712`, `identity-drizzle-repository.test.ts:23-27,101-105`, `content/.../seed.test.ts:91-105`). D-4 정면 위반이며, 소비자가 없어 fixture 표류도 감지되지 않는다.

## 모듈별 소견

### learning (14파일)

가장 성숙한 모듈이다. 도메인 결정 함수(`start-lesson-decision`, `complete-step-effect-plan`, `step-grading-policy`)는 우선순위·replay·불변식을 리터럴 기대값으로 고정하고, `learner-cursor.test.ts`는 payload·서명 위조와 32byte 미만 secret 거절까지 덮으며, `learner-read-mapping.test.ts`는 동률 정렬·빈 page·0%/100% 경계를 갖췄다. `learning-http.test.ts`는 `createApp` + `registerLearningRoutes`를 실제로 조립해 `app.request`로 status·canonical code·`Retry-After`·`Cache-Control`을 검증하므로 D-7을 지킨다.

문제는 세 가지다. 첫째, `learning-drizzle-repository.test.ts`(806줄)가 이미 migration이 만든 `learner_step_drafts` DDL을 손으로 다시 쓰고(`:702-736`) published course 시드도 인라인으로 복제한다(`:737-771`). 둘째, `learning-application.test.ts:237-269`는 fixture가 강제한 `retry` 결과를 그대로 되돌려받는지만 확인해 stub 자신을 검증한다(C-10). 셋째, **구조가 같은 모듈 안에서 갈린다** — 12개 파일은 `src/test/{domain,application,infrastructure}/`에 모였는데 `interface/http`와 `infrastructure/persistence` 테스트만 소스 옆에 남았다. `vitest.workspace.ts`의 `include: ["src/**/*.test.ts"]`가 둘 다 잡으므로 실행에는 문제가 없지만, 새 테스트를 어디 둘지 판단 기준이 없어 유지보수 부담이다. 나머지 4개 모듈은 전부 소스 옆에 두므로 learning을 그쪽으로 통일하는 것이 저장소 전체 규칙을 하나로 만든다(수정 권고 참고).

### content (10파일)

`content-drizzle-repository.test.ts`(801줄)는 partial unique index, published trigger 불변성, asset FK, orphan/reactivate, cutoff 정리, publish rollback을 실제 SQLite에서 검증하는 높은 가치의 통합 테스트다. 다만 `:195-358` 한 테스트가 8단계 시나리오와 14개 assertion을 담아 실패 시 원인 파악이 어렵다(C-8, C-1).

가장 나쁜 파일은 `content-seed.test.ts`다. `:27-30`(14/69/321/831), `:239-250`(step 타입 분포 10건), `:32-89`(첫 row의 제목·설명·요약 3문장 verbatim과 AI target 배열)이 모두 **콘텐츠 재고 목록을 테스트로 복제**한다. `docs/authority-map.md`는 이 값의 작성 원천을 `content-seed-data.json`으로 못박았는데, 오타 수정 같은 콘텐츠 편집만으로 변환 로직과 무관한 테스트가 깨진다(D-6, D-8). `:93-96`은 `satisfies Record<...>`로 타입이 이미 강제하는 상수 매핑 4건을 리터럴과 비교하고(`content-seed.ts:114-131`), `:158-160`은 한 줄 `JSON.stringify` wrapper의 위임을 단정한다(`content-seed.ts:248-250`). 반대로 `:185-216`의 AI 코칭 target 검증과 `:163-183`의 lesson time 거절은 실제 도메인 불변식이라 유지 가치가 높다.

`seed.test.ts`는 목적이 다른 파일인데(변환 단위 ↔ DB 통합) `:23-44`에서 같은 재고 수치를 다시 고정한다. `content-http.test.ts`는 ETag/If-Match 428, 413, multipart 400을 실제 route로 검증해 좋지만, `:295-301`의 fake session이 **cookie가 null이 아니면 무엇이든 admin으로 인증**하므로 인가 실패(403) 경로가 어느 계층에서도 검증되지 않는다. application 3파일은 20개 메서드짜리 `ContentRepository` mock을 각각 복제하지만, "호출되면 안 되는 port는 throw"(`upload-content-asset.test.ts:146-148,152-154,167-169`)라는 설계는 이 저장소 최고 수준이다.

### identity (6파일)

`learner-profile.test.ts:33-64`의 3×3 상태 전이 행렬은 이 저장소에서 가장 좋은 정책 테스트다 — 기대값을 리터럴 표로 고정해 프로덕션 규칙을 복제하지 않는다. `identity-http.test.ts`도 401/403/409/503/400과 `Cache-Control`·`Vary`를 실제 route 조립으로 덮고, session fake가 cookie 값을 정확히 비교한다(`:175`, `:249-250`).

문제는 이름과 계층이다. `identity-service.test.ts:57`·`:121`은 "…port fake를 사용한다"처럼 **테스트 도구를 이름으로 삼아** 방지할 위험을 드러내지 못하고(C-6), `:67`의 `expect(clock.now).toHaveBeenCalledOnce()`는 순수 구현 세부다(C-4). `identity-drizzle-repository.test.ts:96-125`의 "transaction rollback을 보존한다"는 identity repository 함수를 하나도 호출하지 않고 Drizzle/bun:sqlite의 transaction 의미만 확인한다(D-8). `deleted-learner-purge.test.ts:34`의 `expect(deletedLearnerRetentionMs).toBe(432_000_000)`은 D-1 정면 위반이다. `identity-http.test.ts:159`의 표시 이름 정규화 단정은 정규화를 test double(`:230`)이 수행하므로 프로덕션 계약을 검증하지 않는다.

### ai-feedback (6파일)

`ai-feedback-drizzle-repository.test.ts`(746줄)는 lease TTL과 Retry-After 초 계산, 멱등 재생, 동시 요청의 provider 단일 호출, 서울 자정 quota 전환, global/user quota 독립성, maintenance·provider 경쟁, provider 대기 중 write transaction 미점유(`:628-667`)까지 검증한다. 시나리오 선정은 이 저장소 최고 수준이고 `deferred`로 결정론적 동기화를 만들어 sleep이 전혀 없다(C-3 없음). 문제는 조립이다 — 10개 테스트가 `createInMemoryWritingAppDatabase()` → `prepareAiFeedbackDatabase()` → `try/finally close()`를 복제하고 `:670-713`이 published course 시드를 인라인으로 다시 짠다.

`ai-feedback-application.test.ts`도 예약→provider→저장 순서, caller abort, timeout, 저장 실패 보상, 관측 event의 요청 원문 비노출을 실제로 덮는 강한 테스트다. 첫 테스트(`:46-114`)에 5개 개념이 몰린 것만 문제다.

`ai-feedback.test.ts`는 상태가 가장 나쁘다. `:39`는 배열을 복사하는 `createAiFeedback`(`ai-feedback.ts:55-63`)을 깊은 동등 비교로 확인해 복사 여부를 절대 탐지할 수 없고(C-13), `:38`의 `if (response.isErr()) return`은 직전 `expect`가 이미 throw하므로 도달 불가한 죽은 분기다. `:91`의 `const allowed = from === "pending" && to !== "pending"`은 **프로덕션 전이 규칙을 테스트가 재계산**하므로 규칙이 틀리면 함께 틀린다(C-4). `:69-71`·`:118-122`는 기본 정책 객체가 유효한지 단정한다(D-2). 반면 `:132-145`의 서울 자정 경계(14:59:59.250 → 1초, 15:00:00 → 86400초)는 정확히 필요한 경계 테스트다.

`ai-feedback-prompt.test.ts`(32줄)는 6개 assertion 중 5개가 무효다 — `:24`는 상수를 자기 자신과 비교(D-1), `:23`·`:29`는 instruction 원문을 계약으로 삼고(D-6), `:26-28`은 `AiFeedbackPromptInput`이 `{answer, focus, lessonTitle}`만 받으므로(`ai-feedback-prompt.ts:3-7`) 타입상 절대 들어올 수 없는 key의 부재를 확인한다(C-13). `:16-22`의 input 구성 assertion 하나만 남기면 된다.

**`openai-feedback-provider.test.ts`는 C-7도 C-10도 아니다.** 실제 network를 타지 않고, SDK `responses.create` 경계에만 fake를 두고 실제 adapter의 request 구성·응답 파싱·fail-closed·usage 정규화·원문 비노출을 검증한다. `:87`·`:150`의 `not.toContain`은 fake가 실제로 그 문자열을 반환하므로 실패할 수 있는 유효한 assertion이다. 외부 provider adapter에 대한 올바른 seam 테스트다. 단 `:62-67`이 JSON schema `required` 배열의 **순서**를 계약으로 고정한 것은 D-6 위반이고, `timeoutMs`를 세 fixture에 넘기면서 timeout 동작은 이 경계에서 검증하지 않는다.
