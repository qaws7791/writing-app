## Phase 3 · 근본 원인 5개

### R-1. 검증 게이트의 소유자가 없다

만든 증상: F-01, F-02, F-03, F-04, F-19, F-20, F-21
`check:toolchain` 삭제가 workflow 14곳을 깨뜨렸는데 4일간 발견되지 않았다. 그 이유는 CI가 깨졌다는 사실을 CI가 알려주지 못하기 때문이다. 같은 구조로 `knip` 실패, 로컬 build 실패, 무효 lint 규칙 3건이 누적됐다. 게이트는 "추가"되었으나 "게이트가 살아 있는지"를 지키는 게이트가 없다.

**6개월 방치 비용**: 정적 검사·테스트·번들 예산·E2E가 전부 장식이 된다. 회귀는 사용자 보고로만 발견된다. 게이트 복구 시점에 누적된 위반이 수백 건이 되어 한 번에 통과시킬 수 없고, 팀은 게이트를 다시 끄는 선택을 하게 된다. 자동화 투자(현재 정적 검사 8종 + E2E 3 프로젝트 + Lighthouse + k6)가 전액 손실된다.

### R-2. 도메인 언어의 단일 정의가 없다

만든 증상: F-05, F-17, F-24, F-27, F-33
`docs/glossary.md` 13줄은 코드 어휘와 연결되지 않는다. 그 결과 "학습 날짜 경계"가 5가지로, "학습자 식별자"가 4가지로, "레슨"이 전송 DTO 별칭으로 존재하고, 제품에 없는 `ConversationId`가 코드에 남았다. 리뷰가 어휘 분기를 걸러내지 못하는 것은 대조할 정본이 없기 때문이다.

**6개월 방치 비용**: 개념 하나당 표현 수가 계속 늘어난다. 시간대 표현이 지금 5개인데 새 리포팅 화면마다 하나씩 추가되면 정책 변경이 사실상 불가능해진다. 신규 개발자 온보딩에서 "이 두 타입이 같은 것인가"를 매번 코드로 추적해야 하며, 그 판단 실수가 데이터 정합성 버그로 이어진다.

### R-3. 경계 강제를 import 그래프로만 정의했다

만든 증상: F-06, F-07, F-08, F-09
dependency-cruiser는 import edge를 훌륭하게 통제한다. 그러나 모듈이 공유하는 것은 import가 아니라 **하나의 SQLite 파일**이다. 규칙이 import를 막을수록 결합은 (a) `./schema` 공개, (b) raw SQL 테이블명 문자열, (c) app 계층의 직접 DELETE 같은 **타입 검사 밖의 경로**로 이동했다. 경계는 그래프에서 깨끗해지고 데이터 층에서 흐려졌다.

**6개월 방치 비용**: `depcruise` 위반 0을 근거로 "경계가 건강하다"고 판단하는 오류가 굳는다. 새 모듈이 추가될 때마다 purge 누락·SQL 드리프트 위험이 선형 증가한다. 모듈 하나를 별도 서비스로 분리해야 할 시점에 실제 결합도가 측정된 적이 없어 견적이 불가능하다.

### R-4. 계층마다 오류 어휘를 새로 만드는 것을 원칙으로 삼았다

만든 증상: F-14, F-22, F-23
"각 계층은 자기 어휘를 갖는다"를 기계적으로 적용해 에러 타입 44개·매핑 함수 14개가 생겼다. 변환이 늘어날수록 각 변환에서 정보가 조금씩 빠지고, 마지막 단계에서는 원인(`cause`)이 25곳에서 사라진다. `mapOperationsError`처럼 파라미터를 읽지 않는 매퍼는 이 구조의 논리적 종착점이다.

**6개월 방치 비용**: 장애 대응 시간이 계속 늘어난다. 감사 기록 저장 실패가 무흔적이라는 점은 규제 대응 국면에서 "기록이 없다"를 증명해야 하는 상황을 만든다. 새 실패 유형 추가 비용이 3~5곳으로 고정되어 오류 처리를 "추가하지 않는" 선택이 합리적으로 보이기 시작한다.

### R-5. 삭제가 추가보다 어렵게 설계됐다

만든 증상: F-13, F-15, F-16, F-17, F-18, F-30, F-31, F-32
