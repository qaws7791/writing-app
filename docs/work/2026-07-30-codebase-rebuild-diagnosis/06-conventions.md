# 06 · 합의할 규칙과 자동화

규칙은 **자동으로 강제될 때만** 규칙이다. 각 항목에 강제 수단을 명시하고, 강제할 수 없는 것은 리뷰 체크리스트로 내린다.

이 문서는 `AGENTS.md`, `docs/engineering/code-style.md`, `docs/engineering/code-review.md`를 대체하지 않는다. 이 진단에서 **결정적 충돌이 반복 관측된 항목만** 추가하거나 정정한다.

## 2. 오류 처리

| 규칙                                                                                                | 근거 발견                                           | 강제 수단                                                                                                            |
| --------------------------------------------------------------------------------------------------- | --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------- |
| `catch`에서 만드는 실패는 반드시 `cause`를 담는다                                                   | F-22 (25 / 31이 원인 폐기)                          | **커스텀 oxlint 룰**: `catch (x) { ... err({...}) }`에서 `cause` 미포함 시 error. 인프라 존재(`workspace-rules.mjs`) |
| 감사·개인정보·인증 실패는 `cause` 외에 `logger.error`도 남긴다                                      | F-22 (감사 저장 실패 5곳 무흔적)                    | 리뷰 체크리스트 + 통합 테스트 1건                                                                                    |
| `retryable`을 실패 생성 지점에서 결정한다. 전송 계층이 추측하지 않는다                              | F-14 (버그를 503 재시도 신호로 오분류)              | `Failure` 타입의 필수 필드로 강제                                                                                    |
| 계층 간 변환은 **정보를 추가할 때만** 만든다. 이름만 바꾸는 변환은 만들지 않는다                    | F-23 (5중 변환, 타입 44개)                          | 리뷰 체크리스트                                                                                                      |
| 실패 union에 variant를 추가하면 `assertExhaustive*`가 컴파일 에러를 낸다. 이 장치를 우회하지 않는다 | P-10                                                | `typescript/ban-ts-comment: error` (현행) + `.typecheck.ts`                                                          |
| 의도적으로 비운 `catch`는 **왜 비웠는지**를 한 줄 주석으로 남긴다                                   | P-12 (`container-cleanup.ts:57` 등 3곳이 이미 준수) | 리뷰 체크리스트. `no-empty` 규칙은 주석이 있으면 통과                                                                |

### 정당한 빈 catch의 판별 기준

다음 셋을 모두 만족할 때만 허용한다. 그 외의 빈 `catch`는 F-22 대상이다.

1. 이 실패를 보고하는 것이 **더 중요한 실패를 가릴** 수 있다 (예: 정리 실패 보고가 원래 초기화 오류를 덮음)
2. 대안 경로가 이미 실패를 기록하고 있다
3. 주석이 위 두 가지를 명시한다

현행 준수 사례: `apps/api/src/composition/container-cleanup.ts:57`, `apps/api/src/composition/create-container.ts:429`, `apps/api/src/lifecycle/server-lifecycle.ts:274,543`, `apps/api/src/main.ts:69`, `packages/infra/auth/src/learner/server.ts:84`.

### 테스트를 추가할 때 / 추가하지 않을 때

| 추가한다                   | 추가하지 않는다           |
| -------------------------- | ------------------------- |
| 권한·인증 경계 변경        | 상수 값                   |
| 상태 전이와 불변식         | 타입이 이미 강제하는 사실 |
| 트랜잭션·복구 경로         | 한 줄 wrapper의 위임      |
| 재현된 결함                | 정적 markup 존재 여부     |
| 데이터 삭제·보존 정책      | 프레임워크 동작           |
| 외부 계약(wire, migration) | 계층마다 같은 동작 중복   |

정적 검사·타입·lint 룰로 막을 수 있으면 테스트를 쓰지 않는다. Step 3의 `cause` 보존을 24곳 테스트가 아니라 커스텀 lint 룰 1개로 강제하는 것이 그 예다.

## 6. 리뷰 체크리스트

PR 템플릿(`.github/pull_request_template.md`)에 넣을 항목. 자동 강제가 불가능한 것만 남겼다.

**경계**

- [ ] 새 개념을 도입했다면 `docs/glossary.md`에 정본 위치를 추가했는가
- [ ] 기존 개념의 표현을 새로 만들지 않았는가 (시간대·식별자·실패·화면 모델)
- [ ] 모듈 `exports`를 늘렸다면, `./module`/`./http`/`./ports`/`./migration-schema` 중 어디에 속하는지 답할 수 있는가
- [ ] 횡단 관심사를 app 계층에 직접 구현하지 않았는가 (모듈 포트로 표현 가능한지 확인)

**오류**

- [ ] `catch`에서 만든 실패가 `cause`를 담는가
- [ ] 빈 `catch`가 있다면 "3.정당한 빈 catch의 판별 기준" 셋을 모두 만족하고 주석이 있는가
- [ ] 새 실패 variant가 `retryable`을 정확히 표현하는가 (버그를 재시도 가능으로 두지 않았는가)
- [ ] 계층 간 변환을 추가했다면 정보를 **추가**하는가 (이름만 바꾸는 변환이 아닌가)

**삭제**

- [ ] 기능을 제거했다면 선언·검증·테스트·문서·배포 설정을 모두 제거했는가 (F-16 유형)
- [ ] 이 변경으로 호출처가 없어진 코드를 함께 지웠는가
- [ ] 새 확장점·옵션·플래그를 만들었다면 **지금** 소비자가 있는가

**테스트**

- [ ] 이 테스트가 막는 구체적 회귀를 한 문장으로 말할 수 있는가
- [ ] 정적 검사·타입·lint로 대신할 수 있는 것을 테스트로 쓰지 않았는가
- [ ] 통합 테스트 셋업을 인라인으로 다시 짜지 않았는가

**게이트**

- [ ] `bun run build` / `bun run typecheck` / `bun run test` / `bun run ci:static` 전부 통과했는가
- [ ] script를 삭제·개명했다면 workflow·문서·다른 script의 참조를 갱신했는가
- [ ] 설정에서 참조한 경로가 실제로 존재하는가

**문서**

- [ ] 변경이 `/docs`의 서술을 무효화한다면 같은 PR에서 갱신했는가
- [ ] 코드가 소유하는 값(포트·경로·버전·스키마)을 문서에 복제하지 않았는가
- [ ] 문서가 **보장**으로 서술한 동작을 코드가 실제로 보장하는가 (F-25 유형: `lesson-runtime.md:41`이 pagehide flush를 계약으로 서술했으나 코드가 보장하지 못함)
