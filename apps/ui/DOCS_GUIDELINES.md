# Luma UI 컴포넌트 문서 규칙

이 문서는 모든 컴포넌트 페이지가 같은 깊이와 순서로 설명되도록 하는 편집 기준이다. 예제와 설명은 현재 Luma 구현, `DESIGN.md`의 핵심 원칙과 `design/COMPONENTS.md`의 구현 계약에 맞춰 작성한다. Public API를 설명할 때는 `design/GOVERNANCE.md`를, 학습 또는 AI·고위험 기능을 다룰 때는 해당 분야별 문서를 함께 적용한다.

## 1. 문서의 기본 순서

모든 페이지는 다음 순서를 따른다.

1. **개요** — 무엇을 해결하는 컴포넌트인지 한 문장으로 설명한다.
2. **대표 미리보기** — 가장 일반적인 실제 사용 장면을 보여준다.
3. **가져오기** — `@workspace/ui` import 경로를 알린다.
4. **사용법** — 실제 export 이름과 최소 구성을 보여준다.
5. **예제** — 기본, 시각 옵션, 크기, 상태, 조합 순으로 전개한다.
6. **사용 지침** — 적합한 상황, 피해야 할 상황, 상태 관리 기준을 설명한다.
7. **접근성** — 이름, 키보드, 포커스, 상태 전달에 필요한 조건을 설명한다.
8. **Props** — 현재 `@workspace/ui` 소스에서 확인한 공개 prop만 기록한다.
9. **API Reference** — 실제 export 목록과 원본 primitive 문서를 연결한다.

## 2. 예제의 공통 기준

- 모든 컴포넌트에는 최소 4개의 예제 주제를 둔다. 단순 유틸리티는 기본·방향/크기·조합·유의사항으로 구성할 수 있다.
- `variant`, `size`, `orientation`, `side`, `align`처럼 스타일이나 배치를 바꾸는 prop이 있으면 지원 값을 빠짐없이 보여준다.
- 상태를 가지는 컴포넌트는 가능한 범위에서 기본, hover/focus가 가능한 실제 컨트롤, disabled, invalid, loading, empty 상태를 다룬다.
- 값이 있는 컴포넌트는 제어/비제어 사용법 중 혼동 가능성이 큰 쪽을 설명한다.
- 복합 컴포넌트는 단독 예제에 그치지 않고 Field, Label, Button, Badge, Input Group 등 인접 컴포넌트와의 조합을 하나 이상 제공한다.
- 예제는 장식용 샘플보다 실제 제품 문맥을 사용한다. 한국어 레이블과 데이터는 짧고 자연스럽게 작성한다.
- 코드와 미리보기의 내용, prop, 레이블은 서로 일치해야 한다.
- 실행 가능한 예제는 미리보기와 코드를 하나의 경계 안에 배치한다. 미리보기를 먼저 보여 주고 코드는 일부 행만 노출한 뒤 명시적인 버튼으로 전체를 펼친다.
- 코드가 접혀 있어도 전체 코드 복사, 키보드 접근, `aria-expanded`와 focus-visible 상태를 제공한다. 짧은 코드는 불필요한 펼치기 단계를 만들지 않는다.

## 3. Luma 스타일 적용 기준

- 넓은 여백과 여유로운 밀도를 유지하되, 정보가 적다는 이유로 빈 장식을 추가하지 않는다.
- 큰 라운드는 콘텐츠 표면과 오버레이에, 컨트롤은 중간 라운드에, 배지·칩만 pill을 쓴다. 모든 요소에 같은 반경을 기계적으로 반복하지 않는다.
- 완전한 흰색·검정색 대신 Luma 토큰을 사용한다. 예제에서 임의의 강한 강조색을 추가하지 않는다.
- 상태 차이는 색만으로 전달하지 않는다. 텍스트, 아이콘, `aria-*`, `data-*` 상태를 함께 사용한다.
- 오버레이는 제목과 설명을 갖고, 닫기 또는 완료 경로가 분명해야 한다.

## 4. 설명 작성 기준

- prop 이름과 컴포넌트 이름은 코드 표기로 쓴다.
- “할 수 있습니다”를 반복하기보다 먼저 사용 목적을 말하고, 다음 문장에서 제약이나 이유를 설명한다.
- 구현에 없는 prop이나 동작을 공식 shadcn 문서에서 그대로 가져오지 않는다.
- Base UI와 HTML에서 상속되는 전체 API를 복제하지 않고, Luma에서 자주 쓰거나 시각 결과에 영향을 주는 prop을 우선한다.
- 위험하거나 되돌리기 어려운 작업은 `AlertDialog`, 일반 편집은 `Dialog`, 보조 작업은 `Popover` 또는 `Sheet`처럼 선택 기준을 명시한다.

## 5. 접근성 체크리스트

- 아이콘 전용 컨트롤에 접근 가능한 이름이 있는가?
- 레이블과 입력의 `htmlFor`/`id`가 연결되어 있는가?
- 오류가 `aria-invalid` 및 설명 텍스트로 함께 전달되는가?
- 키보드로 열기, 이동, 선택, 닫기가 가능한가?
- 포커스가 열림 전후의 논리적인 위치로 이동하는가?
- 로딩, 진행률, 선택 상태가 보조 기술에 전달되는가?
- RTL에서 방향성 아이콘과 정렬이 의미를 유지하는가?

## 6. 완료 조건

한 페이지는 다음 조건을 모두 만족해야 완료로 본다.

- 대표 미리보기, 가져오기, 사용법, 4개 이상의 구체적 예제 주제가 있다.
- 실제 구현과 일치하는 주요 props 및 export가 있다.
- 사용 지침과 접근성 항목이 각각 2개 이상 있다.
- 다른 Luma 컴포넌트와의 조합 또는 선택 기준이 있다.
- 오른쪽 목차가 페이지의 실제 섹션과 일치한다.
- 라이트/다크 테마와 모바일 폭에서 읽을 수 있다.
